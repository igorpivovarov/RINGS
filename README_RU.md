# RINGS

**RINGS** — экспериментальный проект для исследования того, как последовательно усложняющаяся внутренняя нейронная динамика может поддерживать адаптивное поведение и минимальную само-репрезентацию у простого воплощённого агента.

Агент управляется **спайковой нейронной сетью (SNN)**, реализованной в [Brian2](https://brian2.readthedocs.io/), и действует в среде **Gymnasium/MiniGrid** с едой, опасностями и внутренней переменной энергии. Чтобы выживать, он должен собирать еду, избегать опасностей и регулировать собственный энергетический запас. Основной поведенческий показатель benchmark — время жизни в шагах среды, ограниченное `max_steps`, однако сама нейронная динамика также является основным предметом исследования.

## Исследовательская идея

RINGS основан на идеях **TEVSER (Theory of Evolving Self-Representations)**. В TEVSER усложнение поведения связывается с появлением внутренних репрезентаций, которые позволяют системе различать и интегрировать информацию о собственном состоянии, внешней среде и отношениях между ними.

Проект задаёт намеренно минимальный вопрос:

> **Что меняется, когда агент переходит от прямых связей «стимул → реакция» к устойчивым внутренним нейронным состояниям, которые участвуют в выборе действий?**

Вместо того чтобы сразу строить сложную когнитивную архитектуру, RINGS воспроизводит этот переход поэтапно в небольшой и интерпретируемой спайковой сети. Цель проекта не состоит в утверждении, что конкретный рекуррентный паттерн уже является полноценной биологической моделью Self. Задача — проверить, дают ли механизмы, которые могут быть кандидатами на элементарную само-репрезентацию, наблюдаемые изменения нейронной динамики и поведения.

Одна из центральных гипотез проекта состоит в том, что **рекуррентная аттрактороподобная активность может поддерживать внутреннее состояние, которое не сводится только к текущему сенсорному входу**. Такое состояние потенциально может интегрировать сенсорную, гомеостатическую и связанную с действиями информацию во времени и тем самым служить минимальным субстратом для саморегуляции.

## Последовательность моделей

В репозитории сохранён ряд моделей с постепенно возрастающей сложностью. Это сделано намеренно: простые модели позволяют лучше увидеть вклад каждого нового механизма.

1. **Реактивная модель (R)** — feed-forward управление по принципу «стимул → реакция». Сенсорные входы непосредственно определяют поведение через быстрые нейронные процессы.
2. **Модель с химической модуляцией (C)** — добавляет медленные внутренние модуляторные переменные, отражающие более длительный физиологический контекст, при этом сама нейронная сеть остаётся feed-forward.
3. **Рекуррентные кольцевые модели** — вводят рекуррентные нейронные популяции, способные поддерживать структурированную активность дольше непосредственного сенсорного воздействия.
4. **Связанное рекуррентное состояние (v0.51)** — отделяет устойчивое внутреннее состояние от моторного считывания и позволяет этому состоянию непрерывно развиваться во времени, влияя на поведение.

Такая последовательность позволяет проводить как **механистические сравнения**, так и **абляционные эксперименты**. В одной и той же среде можно отдельно исследовать вклад медленной химической модуляции, рекуррентной динамики состояния и их взаимодействия.

## Зачем нужен RINGS

RINGS задуман не как агент, оптимизированный на максимальный performance, а как компактный вычислительный стенд, в котором внутренние механизмы остаются достаточно простыми, чтобы их можно было наблюдать, записывать, визуализировать и избирательно отключать.

Поэтому проект сочетает три уровня анализа:

- **Поведение:** время жизни, сбор еды, столкновения с опасностями и другие статистики эпизода.
- **Механистические вмешательства:** абляции при фиксированных параметрах и сопоставимые сравнения разных вариантов модели.
- **Нейронная динамика:** записи активности, динамика популяций, траектории рекуррентного состояния и PCA-визуализация пространства состояний.

Это позволяет изучать не только **улучшилось ли поведение**, но и **какой внутренний динамический механизм изменился** после изменения архитектуры.

Текущую кодовую базу следует рассматривать как активно развивающийся исследовательский прототип. Старые версии сохраняются намеренно, поскольку сама последовательность перехода от простых контроллеров к устойчивой рекуррентной динамике является важной частью исследовательской логики проекта.

## Быстрый старт

```bash
# Один записанный эпизод
python3 rings_minigrid_brian_2_prototype51.py --mode run --seed 7 \
  --max-steps 1000 --danger-speed 0.5 --visual on \
  --record on --record-path logs/run51.npz --debug-log logs/log51.csv

# Параллельный подбор
python3 rings_minigrid_brian_2_prototype51.py --mode tune \
  --trials 100 --workers 30 --num-seeds 12 --start-seed 1 \
  --max-steps 1000 --danger-speed 0.5 --output config/rings_best_params_51.json

# Независимая оценка
python3 rings_minigrid_brian_2_prototype51.py --mode evaluate \
  --params config/rings_best_params_51.json --seeds 1001 1002 1003 1004 \
  --max-steps 1000 --danger-speed 0.5 --eval-report logs/evaluation51.json

# Видео 16:9 по записи
python3 rings_neural_video_attr.py logs/run51.npz --output video/run51_attr.mp4
```
## Порядок работы и условия экспериментов

1. Подберите параметры на тренировочных сценариях, затем зафиксируйте их.
2. Оцените результат на отложенных сценариях. Tune prototype51 исключает validation seed из обучения и дополнительно не допускает seed проверочных сценариев 4 и 7 в validation.
3. Запускайте benchmark версий с одинаковой средой, горизонтом и протоколом seed. Для каждого условия используйте новый каталог.
4. Сравните полные seed-группы, затем изучайте выбранные записи для понимания механизмов.

У prototype51 `--params` не задаёт начальные параметры случайного поиска в tune: run/evaluate загружают параметры, select читает checkpoint. Resume использует checkpoint из `--output`. Для сервера на 30 ядер явно задавайте `--workers 30`: у prototype51 по умолчанию 32 процесса (допустимо 1–100), у benchmark — 30, у tune R/C — 1. Режим evaluate сам по себе не является параллельным benchmark.

`--mode select --params SEARCH.json --output SELECTED.json` повторно отбирает кандидатов из `all_results` без нового перебора параметров, но может выполнять проверки кандидатов и потому не обязательно мгновенен. Сохраняйте исходный checkpoint. Checkpoint без `best_params` не является готовым файлом параметров. JSON v0.51 несовместим с более ранними схемами.

В CLI v0.51, R/C и benchmark по умолчанию **опасности неподвижны (`--danger-speed 0.0`)**. Для движущихся явно укажите `0.5`. В v0.51 это одно обновление движения опасностей на два шага среды; заблокированная попытка не обязательно приводит к перемещению. Шаг среды не равен секунде: `snn_step_ms` — время Brian2, скорость видео задаётся отдельно.

Абляция с фиксированными параметрами более непосредственно проверяет эффект удаления механизма, чем отдельная перенастройка каждой абляционной модели. Сравнение перенастроенных моделей отвечает на другой вопрос. В обоих случаях нельзя незаметно смешивать тренировочные и отложенные сценарии.

### Режимы абляции

| Модель | Значения | Значение |
| --- | --- | --- |
| v0.51 | `full`, `no-state-recurrence`, `no-chemistry`, `both` | Полная сеть; абляция рекуррентности состояния; отключение химических эффектов; обе абляции. Это не удаление всех обратных связей агента и среды. |

## Параллельный benchmark

```bash
python3 rings_benchmark.py run \
  --model rings_minigrid_brian_2_prototype51.py --params best51.json \
  --output results_v051 --workers 30 --seeds 100 --repeats 10 \
  --start-seed 1001 --max-steps 1000 --danger-speed 0.5

python3 rings_benchmark.py run \
  --model rings_minigrid_brian_2_prototype51.py --params best51.json \
  --ablation no-chemistry --output results_v051_Ac \
  --workers 30 --seeds 100 --repeats 10 --start-seed 1001 \
  --max-steps 1000 --danger-speed 0.5

python3 rings_benchmark.py report results_v051
python3 rings_benchmark.py compare results_v051 results_v051_Ac \
  --output comparison --allow-different-settings \
  --labels "v0.51 full" "v0.51 no chemistry"
```

По умолчанию 100 seed × 10 повторов = 1000 эпизодов. Повторы используют один seed среды, но разные seed агента. Неопределённость оценивается bootstrap по **средним по seed среды**, а не как по 1000 независимым средам. Повторы не заменяют разнообразия сценариев; фиксированное число запусков само по себе не гарантирует достаточную статистическую мощность.

`compare` принимает два и более каталога. Используется пересечение **полных** seed-групп всех каталогов, минимум две общие группы. `--allow-different-settings` не отменяет это требование. Разные `max_steps` запрещены всегда. Если один набор использует seed 1–100, а другой — 1001–1100, текущая реализация их не сравнит: нужно повторить совпадающие сценарии либо реализовать явно независимый анализ. Нельзя переименовывать seed для искусственного создания пар.

Необходим `manifest.json` и либо `runs/*.result.json`, либо `runs.csv`. При наличии JSON отдельных эпизодов он имеет приоритет. Одного `summary.json` недостаточно. Служебные поля CSV, например `ablation=full`, не являются числовыми метриками. Resume проверяет конфигурацию эксперимента, включая абляцию.

Результаты: `manifest.json`, файлы result/request/log эпизодов, `runs.csv`, `seed_means.csv`, `summary.json`, `performance.png`; сравнение создаёт `comparison.json`, `comparison_settings.json`, `comparison.png`. Первый каталог — база парных разностей. Пропуски и ошибки могут изменить состав полных seed-групп и сместить оценку.

Benchmark импортирует Python-модель, а не передаёт ей произвольные CLI-флаги. Требуются `RingsParams`, `load_params`, `RingsSNNController`, `RingsHomeostasisEnv.step` и `run_episode`, принимающий передаваемые аргументы (`seed`, `params`, `visualize`, `max_steps`, `status`, `record`, `grid_size`, `danger_speed`). Результат должен содержать числовые метрики, включая `steps`; абляция передаётся только при поддержке. Ранние прототипы не все совместимы с этим интерфейсом. `--minigrid-compat` исправляет кодирование объектов, но не общую несовместимость интерфейсов.

## Записи, видео и схемы сети

`--record on` сохраняет нейронные данные; `--debug-log` — CSV по шагам; `--video on` — видео самой модели при выполнении. Это разные функции. CSV недостаточно для восстановления состояний отдельных нейронов. Воспроизведение зависит от схемы записи: NPZ моделей R/C не поддерживается описанными здесь визуализаторами колец/состояния.

Отдельные видеоскрипты не импортируют модель и не запускают Brian2. `rings_neural_video.py` — сохранённый вид колец; `rings_neural_video_attr.py` — карта популяции и PCA для v50/v51. Последний также поддерживает старый режим, но его прежняя компоновка не переводится в 16:9. В новой компоновке среда показана перед действием; решение появляется только в последнем подкадре. История показывает 60 шагов: все 12 входов, состояния, поддержку считывания, моторы и химию. Для каждой строки указана постоянная верхняя граница шкалы.

По умолчанию 30 кадров/с и 3 кадра на шаг дают 10 шагов среды в секунду. `--frames-per-step 6` замедляет видео вдвое при том же FPS. Существующие MP4/PNG не перезаписываются. При прерывании может остаться неполное видео `.partial-…mp4`.

PCA рассчитывается по центрированным следам спайков нейронов состояния, без нормировки индивидуальных дисперсий. Базис рассчитывается один раз по всей записи, даже при выводе фрагмента. Серый цвет — вся ретроспективная траектория, голубой — недавний след, жёлтый — текущая точка. Это не оценка потенциального ландшафта. У разных прогонов независимо рассчитанные базисы PCA различаются; координаты напрямую несопоставимы. `--phase-export` сохраняет базис и координаты для анализа.

Дополнительные `rings_v043_3d.html` и `rings_v051_3d.html` — автономные браузерные просмотрщики **статической анатомии**. Можно вращать, масштабировать, выбирать нейроны, фильтровать связи и использовать соответствующие JSON/GraphML. CLI у них нет, активность из NPZ они не воспроизводят. Статические PNG/SVG схемы — иллюстрации, а не исполняемые скрипты.

## Диагностика и типичные проблемы

```bash
python3 rings_minigrid_brian_2_prototype51.py --self-test --test-report checks51.json
python3 test_rings_RC.py
python3 test_rings_RC_visual.py
```

Тесты R/C должны лежать рядом с обеими моделями. У них нет CLI-параметров; они создают указанные JSON-отчёты, а тест визуализации также `/tmp/RC_visual_*.png`. Проверки оценивают механизмы и интерфейсы, не статистическое качество и не устойчивость аттрактора. `--self-test` prototype51 использует фиксированные сценарии по умолчанию: не добавляйте `--params`, tune и абляции, отличные от full.

- Неизвестный CLI-флаг: проверьте `--help` конкретного скрипта; параметры benchmark не передаются модели автоматически.
- Нет общих полных seed: проверьте диапазоны, ожидаемое число повторов, ошибки и manifest.
- `could not convert string to float: 'full'`: используйте benchmark v1.2.1 или новее с корректной обработкой метаданных CSV.
- Несовместимая запись видео: важна схема записи и поколение модели, а не только имя файла.
- Не считайте обработку Ctrl-C одинаковой во всех исторических tune-скриптах и версиях benchmark; перед новой большой задачей проверьте завершение работников.

Не добавляйте в Git случайно большие записи, видео, checkpoint и каталоги результатов. Условия лицензии приведены в файле `LICENSE` репозитория.

## Справочник JSON параметров моделей

CLI управляет экспериментом, `RingsParams` — сетью. Это поля JSON, **не дополнительные CLI-флаги**. Ниже значения конструктора, а не найденные лучшие параметры. Текущие загрузчики принимают плоский объект параметров или результат tune с `best_params`; перед переносом файлов проверяйте загрузчик конкретной версии. Для отсутствующих ключей могут применяться значения конструктора, но v0.51 при загрузке файла дополнительно требует `g_food` и `selectivity`. Неизвестные ключи v0.51 отклоняются. Суффиксы `_ms`, `_mv`, `_hz` означают мс, мВ и Гц; `g_*` — безразмерные масштабы/приращения в уравнениях проводимости модели, не проводимости в единицах СИ.
